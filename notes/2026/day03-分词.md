## 1. Tokenizer 在做什么

原始文本一般是 Unicode 字符串，例如 `Hello, 🌍! 你好!`。语言模型却是在 **token 序列** 上放概率分布，而这些 token 通常用整数下标表示，例如 `[15496, 11, 995, 0]`。

所以需要一套手续：把字符串 **encode** 成 token，再把 token **decode** 回字符串。讲义里的 `Tokenizer` 就是实现了这两个方法的类：

```python
class Tokenizer:
    def encode(self, string: str) -> list[int]: ...
    def decode(self, indices: list[int]) -> str: ...
```

健全的分词器应当能 round-trip：encode 再 decode，要回到原来那句话。

![Tokenizer 把句子编码成 token 序列，再解码回句子](https://raw.githubusercontent.com/stanford-cs336/lectures/main/images/tokenized-example.png)

*官方讲义图：左边是字符串 “Stanford was founded in 1885.”，右边是一串整数 ID，以及按颜色切开的 token。encode 和 decode 是一对反方向的手续。*

## 2. 先看实际分词器的几个现象

讲义建议先在 [tiktokenizer](https://tiktokenizer.vercel.app/?encoder=gpt2) 上观察，并归纳了三点：

- 一个词和它前面的空格，常常属于同一个 token，例如 `" world"`。
- 同样一个词，出现在句首和出现在句中，表示可能不同，例如 `"hello hello"`。
- 数字往往被切成每隔几位一个 token。

接着，讲义用 OpenAI 的 GPT-5 tokenizer（tiktoken 里的 `o200k_base`）去编码同一句 `Hello, 🌍! 你好!`。按这份讲义跑出来的结果是：词表大小为 **200,019**；这句话变成 8 个 token，能 round-trip 回去；压缩率是 20 个 UTF-8 字节 / 8 个 token = **2.5**。其中 `Hello`、`,`、`你好`、`!` 都会成块出现，而 🌍 在这个词表里被拆到了两个 token 上——单独看那两段并不是合法 UTF-8，但 decode 时拼起来就能还原。

这里的 **压缩率（compression ratio）** 定义为：每个 token 对应多少个 UTF-8 字节。压缩率越大，同样一段文本对应的序列就越短。这对 Transformer 很重要，因为注意力的计算量随序列长度是平方级的。反过来，只靠把 **词表（vocabulary）** 做大，也能把压缩率抬上去，但词表里会出现更多很少见到的 token，也就是更稀疏。

后面比较四种做法时，记住这两个量就够了：词表大不大，压缩率高不高。理想情况是词表受控，同时压缩率还像样。

## 3. 字符分词：词表很大，压缩却不好

一个 Unicode 字符串就是一串 Unicode 字符。每个字符可以用 `ord` 变成码点（整数），再用 `chr` 变回去：`ord("a") == 97`，`ord("🌍") == 127757`。

对 `Hello, 🌍! 你好!` 做字符分词，得到 13 个 token：

`[72, 101, 108, 108, 111, 44, 32, 127757, 33, 32, 20320, 22909, 33]`

它能 round-trip。但问题也很清楚：

- Unicode 大约有 15 万个字符，词表非常大。
- 很多字符其实很少见（例如 🌍），词表用得很不经济。
- 这句话的压缩率大约是 20 / 13 ≈ 1.54，并不高。

讲义的判语是：这是 **两边都不讨好**（worst of both worlds）——词表已经很大，压缩率还是很低。

## 4. 字节分词：词表很小，序列却太长

Unicode 字符串也可以先写成一串字节，再把每个字节看成 0 到 255 的整数。最常见的编码是 [UTF-8](https://en.wikipedia.org/wiki/UTF-8)。有的字符只需 1 个字节，例如 `"a"`；有的要多个字节，例如 `"🌍"` 是 `F0 9F 8C 8D` 这 4 个字节。

同一句话按字节分词，会得到 20 个 token：

`[72, 101, 108, 108, 111, 44, 32, 240, 159, 140, 141, 33, 32, 228, 189, 160, 229, 165, 189, 33]`

好处是词表很小，固定为 **256**。坏处是压缩率正好等于 **1**：一个字节就是一个 token，序列几乎没有被缩短。Transformer 的上下文长度有限（注意力是平方级的），序列一长，能放进窗口的文本就变少了。这就是第 2 天说的：直接在原始字节上建模很优雅，但以今天的模型结构来看，计算上并不划算。

## 5. 词分词：压缩好，词表却收不住

更接近经典 NLP 的做法，是按词切开。讲义用正则 `\w+|.` 处理 `I'll say supercalifragilisticexpialidocious!`，得到的块是：

`I` / `'` / `ll` / 空格 / `say` / 空格 / `supercalifragilisticexpialidocious` / `!`

再把每个块映射成整数，就成了一个 Tokenizer。好处是：每个 token 往往有意义，因为词本来就是人切出来的；压缩率也高，这句话是 44 个字节 / 8 个 token = **5.5**。

但问题也不少：

- 很多词很稀有，模型几乎学不到它们。
- 这样不会自然得到一个固定大小的词表，词表可以随着训练语料变得非常大。
- 训练时没见过的新词只能用一个特殊的 `UNK` token，既难看，也会把困惑度（perplexity）算乱。

## 6. BPE：从数据里学出词表

**Byte Pair Encoding（BPE）** 由 Philip Gage 在 1994 年提出，最初用于数据压缩；2016 年被 [Sennrich et al.](https://arxiv.org/abs/1508.07909) 改编到神经机器翻译里（在那之前，论文里常用的还是词分词）；后来又被 [GPT-2](https://cdn.openai.com/better-language-models/language_models_are_unsupervised_multitask_learners.pdf) 采用。

基本想法是：在原始文本上 **训练** 分词器，得到一份为这份数据定制的词表。直觉是：经常一起出现的字节序列，就用一个 token 表示；罕见的序列，则拆成多个 token。这和第 2 天说的“自适应计算”是同一件事：把更多建模容量留给更有信息的部分。

做法很简单：先把每个字节当成一个 token，然后反复找到当前相邻 token 对里 **出现次数最多** 的那一对，把它们合并成一个新 token，直到合并足够多次为止。

讲义用 `the cat in the hat` 做了 3 次合并。这句话有 18 个字节。按讲义代码（出现次数并列时，会取当前序列里先数到的那一对），三次合并是：

| 步骤 | 合并 | 新 token | 合并后的序列 |
| --- | --- | --- | --- |
| 起始 | （每个字节各算一个 token） | — | `t h e _ c a t _ i n _ t h e _ h a t` |
| 第 1 次 | `t` + `h` | `th`（编号 256） | `th e _ c a t _ i n _ th e _ h a t` |
| 第 2 次 | `th` + `e` | `the`（编号 257） | `the _ c a t _ i n _ the _ h a t` |
| 第 3 次 | `the` + 空格 | `the `（编号 258） | `the_ c a t _ i n _ the_ h a t` |

三次之后，18 个字节变成 12 个 token，压缩率是 1.5。注意空格被并进了 `the `——这已经能让你体会到，前面说的“词和它旁边的空格常常在同一个 token 里”，是数据里真的经常一起出现，而不是人工规定的。

训练得到的是两样东西：一份 **词表**（编号 → 字节串），以及一份 **合并规则**（哪两个旧编号合成哪个新编号）。编码一句新文本时，先把它写成字节，再按这些合并规则依此合并。例如用上面这 3 条规则去编码 `the quick brown fox`，开头的 `the ` 会被合成一个 token，后面的 `quick brown fox` 仍是一个个字节。解码则更直接：按编号查词表，把字节串拼起来，再按 UTF-8 还原成字符串。

这只是讲义里的教学实现，为的是把原理看清楚。Assignment 1 还会在此之上要求：编码时不要盲目扫过全部合并、要识别并保留特殊 token（例如 `<|endoftext|>`）、加入预分词（如 GPT-2 的正则），以及把实现做快。我们这个月先不做作业，知道“课上的草图”和“能用的分词器”之间还有这些差距即可。

把四种做法放在一起看，对照关系就清楚了：

| 做法 | 词表大小 | 压缩率（本讲例子） | 主要问题 |
| --- | --- | --- | --- |
| 字符 | 约 15 万 | 约 1.54 | 词表大、很多字符很稀有，压缩又不好 |
| 字节 | 256 | 正好 1 | 序列太长 |
| 词 | 随语料膨胀，收不住 | 本例 5.5，通常较好 | 稀有词、新词只能靠 `UNK` |
| 实际 GPT-5 tokenizer | 200,019 | 本例 2.5 | 这是 BPE 一类方法在大规模数据上训出来的结果 |

## 今天可以先停在这里

如果抓住了下面几条，今天就够了：

- Tokenizer 做的是字符串和整数 token 之间的双向转换，而且应当能 round-trip。
- 压缩率是“每个 token 对应多少字节”；压缩率更高，序列更短，对平方级的注意力更友好。只靠把词表做大，会带来稀疏。
- 纯字符、纯字节、纯按词切，都明显不理想。
- BPE 是一种数据驱动的启发式：从字节出发，反复合并最常见的相邻对，从而为这份数据定制词表。
- 分词目前仍是模型外面的单独一步。以后也许会直接从字节端到端地学，但无论哪种方案，模型都需要在序列的“块”上工作，而且这些块最好是可变的，好把更多容量分给更有信息的部分。
